# Caching, query performance and resource budgets

Inherit [governance](../governance.md). Activate this module when changing cache semantics, optimizing measured performance or introducing concurrency/resource limits. A slow-looking expression is not evidence that a cache or distributed architecture is needed. Use [data contract](../templates/data-contract.md) and [acceptance](../templates/acceptance.md).

## Establish the bottleneck and contract

Start with a concrete operation and its workload. Record input size, tenant distribution, relationship density, hot keys, concurrency, read/write mix and dependency behavior. Identify whether time is spent in database work, network waits, lock contention, serialization, CPU, allocations or queueing. A cache can hide a query problem while introducing stale permissions and invalidation complexity; an index can improve a read while slowing high-volume writes. Choose the smallest change that addresses observed or clearly reasoned cost.

Define the user's consistency expectation alongside the latency target. If a user changes a value and immediately reloads it, stale data may look like a failed save. If an administrator revokes access, a cached response may expose protected data. Decide whether reads require authoritative state, version-aware cache entries, explicit pending/freshness information or an approved bounded-stale projection. The skill must not invent a TTL and present it as correctness.

## Cache lineage and invalidation

For each cache, write key dimensions, stored projection, source/version, population owner, expiry, mutation triggers, invalidation mechanism, fallback and observability. Include tenant and relevant authorization scope. A shared count or autocomplete list may leak information even when detail endpoints are protected. A signed file URL is not a harmless public string simply because it is cached.

Trace update, delete, relationship reassignment, default change, permission revocation and import correction. Invalidation before commit can allow a concurrent reader to repopulate the old value; invalidation after commit can fail. The adopted design needs a recovery story, not necessarily a new messaging framework. Existing versioned keys, transactional intent or bounded staleness may be appropriate when their guarantees meet the project contract.

Distinguish absence from failure. Caching a dependency timeout as an empty list can turn a temporary outage into a durable lie. Negative caching must identify what absence means, how long it is valid and who can observe it. Refresh failures need explicit handling: preserve permitted stale content, surface unavailable state or reject the operation according to policy. Do not silently serve a stale authorization decision because it improves availability.

## Resource and performance verification

Use controlled fixtures before load generation. Inspect whether a benchmark writes data, sends messages, changes baselines or contacts external services. A read-only audit can inspect existing measurements and query source; it does not authorize production stress testing. Record warm/cold cache, representative data, concurrency, sampling duration and environment. Compare distributions where meaningful rather than reporting only one average.

Test saturation paths as well as speed: connection exhaustion, full queue, slow consumer, hot-key refresh, oversized payload and downstream throttling. Verify admission/backpressure semantics and recovery when capacity returns. Raising every timeout and pool size can increase tail latency and memory pressure; changes need a named bottleneck and measured tradeoff.

For query optimizations, verify deterministic ordering, tenant scope, aggregate correctness and pagination after joins or batching. For caching, exercise an update followed by reload, permission change, failed refresh, simultaneous misses and deployment with an old entry. A benchmark pass does not prove security or business correctness; acceptance includes both.
