# Schema evolution, backfills and data reconciliation

Inherit [governance](../governance.md). Use [migration plan](../templates/migration-plan.md) before generating a migration or backfill. Creating a reviewed source change does not authorize applying it to any database. Exact DDL behavior, transactional support and online operations depend on the selected engine/version and deployment topology.

## Build a phase-by-phase plan

State what each application version can read and write at each phase. For a field replacement, adding the new field is only the beginning: identify who populates it, how old writers affect it, how concurrent edits are resolved, when readers switch and when the old field can be retired. A dual-write period creates two representations that must have explicit precedence and reconciliation; it is not permission for competing owners. Prefer a smaller compatible change when it meets the requirement.

Inspect scheduled jobs, imports, reports, admin scripts and deployment rollback images. A rarely used export can be the last consumer of a removed column. A queued payload created before rollout may be processed by new code afterward. Include legacy records that predate current validation and rows with missing or contradictory values. A clean schema created from scratch does not establish safe upgrade behavior.

For each phase record preconditions, exact source artifact, target environment, executor, expected locks/runtime, cancellation behavior, validation, rollback/forward-repair and next-phase gate. Do not embed credentials or production IDs in reusable migration instructions. Link the owning repository and reviewed artifact; manual operational corrections must be reconciled back to source so redeployment does not revert them.

Database commands have operation-specific locking and validation behavior. PostgreSQL's ALTER TABLE reference documents details that vary by subcommand; it is evidence for checking exact operations rather than a general promise of online safety. [PostgreSQL ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html). Consult the deployed engine's versioned documentation and actual workload before making lock-duration or zero-downtime claims.

## Backfill under live change

Choose stable traversal/checkpoint semantics. Paging by an offset while updating the selection predicate can skip rows; a moving timestamp boundary can continually admit new records. Define a high-water mark, key ordering or other appropriate strategy and how newly arriving records are handled. Checkpoints must represent committed work, not merely fetched batches. If a batch rolls back, its checkpoint must not advance past lost work.

Decide how to handle a record changed after it was read. A conditional update on source/version can prevent stale backfill from overwriting a newer user value. Conflicted rows may be retried or quarantined according to policy. Do not silently choose the migration's older value because the process is called authoritative. For computed values, identify which version of the business calculation applies and whether historical values are intentionally preserved.

A rerun should converge on the same desired state or explicitly detect incompatibility. Test interruption after read, after some writes, after commit before checkpoint acknowledgement and after checkpoint persistence. Define whether a transaction covers one record, batch or entire operation and why. Avoid holding a large transaction merely to make the script appear atomic when resource pressure and rollback time would become unacceptable.

## Rehearsal and release evidence

Rehearse with representative legacy shapes, data distribution and concurrent writers on the actual engine where feasible. Measure lock waits, long-running transactions, replication lag, batch throughput and application behavior. A successful tiny-fixture migration provides syntax and logic evidence only. Production timing remains unverified without a representative workload and environment.

For destructive changes, test recovery of the actual required facts and relationships, not just whether a backup file exists. Recovery objectives belong to the project. An application rollback may fail against a contracted schema; a down migration may remove newly collected data. Document that asymmetry and choose a supported forward repair when appropriate.

Finish by reconciling row/value invariants, dependent projections, search/cache invalidation, documents/exports and background jobs. Record ambiguous/failed records rather than hiding them behind a total count. Keep one authoritative migration history and remove only task-created failed experiments. No live execution, backfill or cleanup is implied by specification or source review alone.
