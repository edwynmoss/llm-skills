# Transactions, contention, idempotency and uncertain outcomes

Inherit [governance](../governance.md). Use [mutation and recovery contract](../templates/mutation-recovery.md). A transaction, lock, retry policy and idempotency key solve different problems. Select mechanisms from an explicit invariant and actual engine/provider guarantees, not from the presence of async code.

## Start with the race, not the mechanism

Write an interleaving: A reads invariant; B reads invariant; A writes; B writes. State which result is forbidden and why. For capacity, two independently valid prechecks can exceed the limit; for editing, a blind update can replace a newer value; for approval, repeated completion can apply an aggregate twice. Inspect existing constraints and conditional updates before reporting a defect. A single atomic decrement with a capacity predicate may already solve the problem without a distributed lock.

Select isolation based on the invariant and the database's documented behavior. Isolation names do not mean identical things across engines. In PostgreSQL, serializable transactions can abort and require transaction-level retries; this is a specific engine behavior, not permission to wrap every backend operation in a retry loop. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html). Read exact deployed-version guidance before using error codes, lock clauses or retry semantics.

Optimistic concurrency must be enforced at the write boundary. A version in a request that is compared before an unguarded update still has a race. A conditional update must inspect whether it affected the expected record and distinguish conflict from not-found/denied according to policy. Pessimistic locks require a consistent acquisition order, bounded wait and known scope; keeping a lock while waiting for a remote service can turn one slow dependency into contention across the system.

## Define idempotency as a lifecycle

Identify logical operation, caller/tenant and payload meaning. Specify whether reusing a key with changed input is rejected, how two simultaneous requests select an owner, and what later callers see while processing is unresolved. The deduplication record and canonical mutation must have a coordinated crash story. Recording a key only after an external effect leaves a duplicate window; recording it before the effect without recovery can permanently suppress work after a crash.

Store only the information needed to reproduce or reconcile the outcome, with the appropriate privacy and retention policy. A request fingerprint should use canonical semantics where required; serialization order alone may not distinguish or equate the right requests. Decide whether result replay returns the original representation or a stable reference to current state, and whether current authorization is checked before replay. A dedupe cache that expires is not a permanent uniqueness invariant.

Consider response loss after successful commit. The client may have no acknowledgement while the database already holds the result. A retry with the same operation identity should follow the adopted reconciliation/deduplication contract. If the provider offers neither a safe repeat nor an outcome lookup, report uncertainty and preserve evidence for resolution. Do not promise automatic recovery merely because the transport library can retry.

## Failure and recovery table

For each boundary, record: durable facts before the step; effect attempted; evidence available on success/failure; whether outcome can be unknown; next safe action; who owns retry; and what a competing caller observes. Include crash before transaction, during writes, after commit before response, after event intent before publish, after remote dispatch before receipt, and after receipt before local acknowledgement when those steps exist.

Separate transaction rollback from compensation. Releasing a reservation after a failed downstream operation may be a business command with its own permissions and failure modes. A sent email cannot be unsent by rolling back the database. A refund is not the same as erasing a charge. The workflow must reflect these facts rather than returning a generic rollback-success label.

## Observable tests

Use barriers, controlled provider responses and explicit transaction interleavings in authorized fixtures. Do not rely on repeated random requests or sleep timing to demonstrate a race. Assert canonical rows, versions, balances/counts, dedupe records, emitted effects and caller-visible outcomes. Include a legitimate second distinct operation to prove deduplication is not suppressing unrelated work. Include changed payload under the same key and two tenants using the same caller-supplied key.

Mocks can establish orchestration and error mapping but cannot prove the selected database's isolation or a provider's idempotency guarantee. A read-only audit should name the exact interleaving and existing guard, then state the smallest controlled real-boundary check. Passing tests for a lock helper alone do not certify the whole use case's concurrency contract.
