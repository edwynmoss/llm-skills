# API and protocol contracts

Inherit [governance](../governance.md). This module applies to external or internal protocol boundaries: HTTP, RPC, GraphQL, command interfaces and streaming transports. HTTP-specific advice applies only to HTTP. Optional working formats: [service contract](../templates/service-contract.md) and [request pipeline](../templates/request-pipeline.md); a projection-only change does not require a new pipeline artifact. The protocol contract is shared with callers and UI skills; it is not an independent business owner.

## Specify the operation before its handler

Record the authoritative schema and where it is enforced. Types in generated clients do not validate malicious requests at runtime. A controller validator may reject malformed input while the domain rejects a well-formed but invalid transition; database enforcement protects races and alternative writers. These responsibilities can share definitions where the framework supports it, but they are not interchangeable. Document which layer owns normalization and whether clients see the original value or normalized persisted value.

For each field, define allowed type, absence, nullability, defaulting, units, precision, identity and edit permissions. Keep integers, money, decimals, date-only values, instants and local times distinct. If a caller omits a value, do not assume it means zero or clear. If a system creates a default, identify whether it is evaluated on every read, copied on creation, or intentionally snapshotted. These decisions also govern import and retry behavior. A JSON schema may describe shape without expressing those business semantics.

Model outcomes as a table: condition; whether the use case ran; whether state may have committed; response code/body; retry eligibility; operation/status lookup; caller action. Include authorization rejection, validation rejection, not found/existence-hidden, optimistic conflict, domain lock, known rollback, dependency timeout before dispatch, timeout after dispatch, durable acceptance with pending work and completion. Use only reachable outcomes. Do not add a polling resource to a synchronous operation merely to fill a template.

HTTP idempotence concerns intended request effects; it does not imply identical responses or guarantee a particular application's remote side effects. Conditional requests can express preconditions, but the storage mutation must enforce them atomically. Follow the adopted protocol and consult its exact definitions rather than inferring safety from an endpoint name. [HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html). A problem-details envelope is a standardized error representation; it does not select the application's domain codes, disclosure policy or remediation. [Problem details](https://www.rfc-editor.org/rfc/rfc9457.html).

## Edge-case acceptance

Test inconsistent content type/body, unsupported media, duplicate query fields, unknown enum values, overlong names, zero/negative/boundary amounts, precision loss, timezone boundaries and empty collections where relevant. Validate nested field paths that the frontend can associate with the correct child. A new client may send fields an old server ignores; document whether ignoring is safe. Mass-assignment protection must apply to fields such as tenant, owner, status, price and approval—not simply to top-level object names.

For pagination, write down the exact consistency promise. Offset pagination over changing data can shift records; a cursor requires an ordering/filter/identity contract and may also need a snapshot policy. Neither is automatically wrong. Verify changes at the page boundary under the promised model rather than claiming universal no-duplicate behavior. Cursor tampering, mismatched filters and revoked permissions are distinct cases. Bulk endpoints need per-item identity and outcome semantics, not a single success flag hiding partial work.

For compatibility review, inspect clients rather than assuming additional fields are harmless. Include enums, unknown values, numeric serialization, nullability, error codes, sort order, response envelopes and generated SDK behavior. Avoid changing a failure status just to make a frontend test pass; reconcile both sides against the shared contract. A successful handler unit test does not prove routing, middleware, serialization, streaming or gateway behavior.
