# Database design, relationships and query behavior

Inherit [governance](../governance.md). Apply this module to relational, document, key/value, graph and object-storage persistence according to their actual guarantees. A SQL-specific constraint or isolation example must not become a universal requirement for another engine. Record the selected engine, version, driver, ORM, deployment topology and connection role in [data contract](../templates/data-contract.md).

## Define constraints by meaning

For each invariant, state the participating fields/records, all writers, allowed exceptions and enforcement boundary. Examples include uniqueness within tenant and lifecycle scope, parent existence, nonnegative remaining capacity, immutable approved values and one active association. The database can enforce some directly; others need an atomic conditional mutation or a transaction. A pre-insert exists check is useful feedback but is not equivalent to a unique constraint under contention.

Inspect the selected database's actual behavior for nulls in unique constraints, collation, case sensitivity, precision, generated values, partial indexes and foreign-key enforcement. A test substitute may differ. Do not universally require a relational foreign key in a document store; define the equivalent ownership, consistency and repair strategy. If the engine cannot enforce the invariant atomically within the selected model, surface the tradeoff rather than pretending application validation closes the gap.

Record deletion separately from visibility. Soft-deleted records may still participate in uniqueness, billing, retention, relationships or audit evidence. Decide whether re-creation restores an old identity or creates a new one, and what happens to dependents. A query filter hiding a row is not proof that its data was deleted or its obligations reconciled. Hard deletion may need object-storage and export cleanup, but do not delete historical evidence without an adopted retention policy.

## Inspect ORM and driver behavior

Read generated queries or existing instrumentation where authorized. A navigation property can trigger one query per row; a joined collection can multiply rows and distort pagination or aggregates. Partial projections can be efficient but dangerous when later treated as fully populated entities for updates. Examine tracking, identity maps, eager/lazy loading, detached updates, serialization and transaction boundaries before refactoring data-access code.

Keep external provider models and database entities from becoming unreviewed public contracts. Map only when the boundary needs a stable projection; do not create trivial mapping layers for every object without a real reason. Verify field-level authorization and sensitive-column selection, including exports and debugging endpoints. A query that retrieves every field and removes secrets only in one controller leaves alternate consumers exposed.

Check resource lifetime under cancellation, exceptions and streaming. A lazy sequence may hold a connection after the handler has started sending a response. A transaction wrapper may open another connection in a repository call and defeat atomicity. Tenant context stored at session scope may leak through the pool unless correctly reset. Verify the actual provider's transaction enlistment and pooling behavior rather than relying on class names such as UnitOfWork.

## Query and data acceptance

Use realistic distribution as well as row count: skewed tenants, duplicate sort values, nulls, long values, wide rows, dense relationships and hot keys. Compare plans and resource behavior under the relevant database version. An explain variant can execute a query or acquire locks; inspect its side effects before using it in a no-change review. Do not run write-capable plans or production load tests without the corresponding scope.

Test schema enforcement through more than the happy-path service method when meaningful: two concurrent creates, direct repository conflict, invalid relationship, duplicate external identifier and removal/reassignment. Confirm the mapped API/domain error remains predictable. For derived data, prove which mutation triggers recomputation and how stale projections are detected/repaired. Repeated imports and reduced input must converge without leaving ghosts.

A passing SQLite or in-memory fixture establishes only its own behavior. Use the actual selected engine for claims about isolation, DDL, collation, JSON operators, locking, query plans and provider-specific constraints. Report unavailable database evidence explicitly while still documenting the source invariant and the smallest real test needed.
