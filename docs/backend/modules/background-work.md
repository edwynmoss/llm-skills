# Jobs, events, webhooks and durable work

Inherit [governance](../governance.md). Use [dependency contract](../templates/dependency-contract.md) and [mutation/recovery](../templates/mutation-recovery.md). Identify the actual producer, durable work owner, delivery mechanism, consumer and canonical effect. A new scheduler or importer must not compete with an existing producer for the same business journey.

## Delivery is not one guarantee

Describe what each acknowledgement proves. A publisher confirmation can indicate broker acceptance while consumer processing has not occurred. A consumer acknowledgement can be lost after the effect committed. A webhook HTTP success may mean the receiver accepted durable work rather than completed it. These boundaries require separate evidence and status. RabbitMQ explicitly distinguishes publisher confirms from consumer acknowledgements; use that distinction when relevant without importing RabbitMQ semantics into other providers. [Acknowledgements and confirms](https://www.rabbitmq.com/docs/confirms).

Do not use exactly-once as an unqualified system claim. State the scope: one canonical transition under a unique key, one visible message under a provider's dedupe window, or one committed database effect despite repeated deliveries. If an external provider does not support deduplication or lookup, the uncertainty remains. A broker's delivery mode does not prove the behavior of a database, payment provider, email gateway or downstream consumer.

## Work-item lifecycle and ownership

Define identity independently from display text. Record producer event ID, canonical entity ID, logical operation ID, processing attempt and provider receipt as separate facts when they differ. Reusing an attempt ID as the business identity can create duplicates on retry; using a broad entity ID as the only dedupe key can suppress legitimate future operations. Tenant scope must be part of the adopted matching policy.

Choose a recovery owner for each state. Pending work must survive process restart; in-progress work needs lease/visibility semantics; completed work needs evidence; exhausted or ambiguous work needs a visible resolution path. A dead-letter queue is a holding place, not a business-resolution policy. Define who may replay, how inputs are checked against current schemas/permissions and how outcomes are reconciled with already-applied effects.

For scheduled work, distinguish intended schedule, actual start, last completed run and business freshness. A heartbeat can show a process alive while its last successful job is stale. Overlap control should protect the logical job scope, not simply one process instance. A lease that expires does not stop the previous worker; use the concurrency module for stale-owner protection where necessary.

## Failure probes and positive controls

Exercise crash before durable acceptance, after acceptance before enqueue, after enqueue before response, after effect before acknowledgement and during retry scheduling where those boundaries exist. Deliver two identical events concurrently, a late old event, a different valid event for the same entity, malformed payload and unknown identity. Verify final canonical state, receipt/dedupe evidence, retry ownership and user-visible status.

Simulate provider outage and recovery without contacting live recipients unless explicitly authorized. Confirm retries do not multiply at transport, SDK, consumer and scheduler layers simultaneously. Test shutdown with work in progress: stop intake, finish or safely release ownership, preserve checkpoint and avoid acknowledging uncommitted work. A cancellation flag alone does not prove a remote operation stopped.

Recognize correct existing mechanisms. A durable job table, unique constraint and conditional completion update can satisfy the required contract without introducing a broker or saga framework. A deterministic source review can identify the crash window and existing guard; actual delivery guarantees need the relevant broker/provider boundary exercised and observed.
