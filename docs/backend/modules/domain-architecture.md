# Domain ownership, use cases and architecture

Inherit [governance](../governance.md). Apply this module to backend implementation, refactoring and business-rule changes. It defines responsibilities without prescribing folders, microservices, a repository pattern or a class hierarchy. Record real ownership inline for a small delta; [service contract](../templates/service-contract.md) provides structure when needed.

## Trace the real journey

Start at a concrete user or system action. Follow its actual command path, not just a similarly named service. Identify authentication context, permission checks, validation, calculations, state transitions, storage writes, emitted events and downstream consumers. An import may bypass the controller while still correctly calling the same use case; credit that reuse. Conversely, two paths may render similar output but differ in locks, rounding, validation, relationships or audit evidence. Verify the invariant at the layer all relevant paths actually share.

Use business vocabulary already established by the repository. Do not introduce an OrderManager merely because several unrelated operations mention orders. Separate a reservation command from a reconciliation job if they have different ownership and lifecycle, while keeping common invariant logic in the canonical owner. Avoid moving one-line expressions into files only to make a layering diagram look complete. A thin route can call a well-scoped function directly; architecture quality is about responsibility and dependencies, not the number of indirections.

Name every fact's lifecycle. Is available capacity entered, computed, reserved, settled or materialized? Does a readiness badge mean parsed, linked, validated, approved or usable? Those facts may be distinct. Never collapse them into one boolean because a UI only displays two colors today. Equally, do not introduce additional persistent state where an existing canonical record can derive the answer cheaply and consistently. Record invalidation and reconciliation when materialization is necessary.

## Boundary changes and pattern selection

Before adding an interface, identify who depends on it and why substitution is needed. An external SDK with provider-specific errors may justify a narrow Adapter because the application needs a stable semantic boundary. Two providers still need genuinely compatible semantics before sharing one interface. A facade that merely renames every SDK method adds maintenance without isolation. A Strategy is appropriate when adopted policies differ by product or region; a conditional with two trivial branches may be clearer. Record why the chosen form fits the actual variation.

A transaction boundary is a use-case concern coordinated with persistence. Domain rules should not query arbitrary provider services or read ambient request globals. Pass required facts and dependencies explicitly; if an invariant depends on changing storage state, enforce the final decision under the selected concurrency mechanism. A pure preflight validation is useful feedback but not necessarily the final authority. Avoid long transactions spanning slow provider requests unless a documented architecture truly requires them.

Shared code must remain generic in meaning, not merely in naming. A utility named normalizeData that secretly applies one business's lifecycle rules belongs to that domain. Likewise, splitting one workflow across many generic helpers can obscure the invariant and its transaction. Extract coherent responsibilities with observable contracts; keep related operations together when they must be understood and changed as one unit.

## Acceptance and positive controls

Trace a normal manual mutation and one alternative writer through the same owner. Exercise creation, modification, reload, removal, conflict and approved/locked behavior where relevant. Compare canonical identities and derived outputs, not screenshots or row counts alone. For defaults and overrides, test explicit zero/false values separately from absence; truthiness is often the wrong inheritance rule.

A correct existing design may use a framework ORM directly from a focused use case, a small switch rather than a Strategy, or one table rather than an event-sourced aggregate. Do not mark those as defects without a violated contract or concrete maintainability consequence. A recommendation must state its tradeoff and migration cost. Source review can establish responsibility placement and call paths; runtime parity requires actual boundaries and consumer evidence under the verification module.
