# Backend governance and applicability

Revision 1.2-public.1. This library owns reusable engineering guidance, not project business policy. Its three entry skills separate specification, implementation and verification. Detailed modules load by applicability. Source provenance is in [sources](sources.md); unresolved project choices are in [decisions](decisions.md).

## Authority and rule interpretation

The authoring mandate is a backend counterpart with the depth of the UI library, including middleware and databases. USER means this mandate and supplied engineering instructions. POLICY means the library maintainer's proposed reusable engineering policy, adopted for skill guidance but not an invented business requirement. SOURCE means a narrowly attributed external fact; it does not confer project authorization. PROJECT means inspected repository rules, API schemas, database constraints, approved decisions and current configuration. A source at a revision is not evidence of deployed behavior.

Every canonical rule has six columns: stable ID; applicability and strength; authority and reason; expected behavior; exceptions/dependencies; observable acceptance. MUST applies only when its applicability predicate holds. CONDITIONAL activates only for the named concern. DEFAULT WITH OVERRIDE needs a concrete local justification for departure. PRODUCT DECISION REQUIRED identifies a choice the skill must not invent. A shared default cannot waive stricter applicable project instructions. If a project contradicts a security or integrity requirement, surface the conflict and a supported repair; do not silently normalize the risk or rewrite policy during an audit.

## Required module routing

Read this file for every entry. Read whole applicable modules, including procedures below rule tables; a rule ID mention is not a substitute. Previously loaded unchanged material need not be read repeatedly. Combining UI and backend skills does not duplicate ownership: both reference the consuming project's same API/domain contract.

Templates are working formats, not an additional reading checklist. References to using a template in this library mean load it when its structure is needed to produce or review the corresponding artifact. A small inline delta can record scope, owner, changed behavior, affected consumers, assertions and evidence directly, without opening templates that repeat already loaded module guidance. This does not waive contract coverage, a required cross-layer impact matrix or the explicit migration-plan prerequisite before generating a migration/backfill. Load gap analysis when a coverage investigation needs its concern matrix, and the decision register when a consequential project choice remains unresolved. Do not read either merely to restate a fully supplied contract.

For supplied snippets, fictional fixtures or an incomplete brief without a repository, those artifacts define the inspection boundary. State unavailable repository/revision/runtime evidence once; do not search an unrelated checkout, infer hidden code, or require Git initialization. Inspect a real repository only when the task supplies or clearly identifies one. Distinguish explicit fixture guarantees from assumptions that need confirmation in a real system.

Implementation always reads domain/architecture and verification. Review always reads verification. Security loads for any affected permission or untrusted boundary; persistence loads when actual storage semantics matter. A read-only endpoint still needs tenancy/security when scoped data is returned. Middleware work may activate concurrency if it changes retries or cancellation, and operations if it changes logging or shutdown. Do not infer relevance merely from directory names.

Route recovery by its actual boundary: transaction rollback, contention, retries and uncertain commit use concurrency; remote outcome lookup, provider reconciliation and repeat safety use integrations plus concurrency; durable message redelivery uses background work. Add operations only when the task also concerns process lifecycle, restore/failover, operational signals or an operator-run procedure. Mentioning a possible operator handoff does not itself require a full operational runbook.

## Common routes and depth

For an existing response-format fix: inspect its schema, clients and error mapping; read API and verification, plus domain for implementation. Reuse existing authorization and persistence behavior unless the diff actually changes it. For a cross-tenant leak: read security, API, persistence and any cache involved; trace selectors, response fields, exports, background consumers and permission revocation. A frontend filter is not an access-control repair.

For a write endpoint: trace identity, middleware, command validation, business policy, atomic storage changes, remote effects and all read models; read API, domain, security, persistence, concurrency and verification. Include jobs/integrations/cache only if those dependencies exist. For a schema rollout: read persistence, migrations and operations, plus every affected writer/reader. For a queue handler: read background work, concurrency and relevant domain/storage/integration modules. A queue does not automatically justify event sourcing, sagas, an outbox or a service split.

For a read-only pilot, choose one representative existing journey. Inspect source, tests and local contracts; provide findings inline. Expanding to adjacent callers is appropriate when evidence shows a shared invariant, not merely because more code exists. Report both existing protections and risks. No defect quota, architecture-score quota or mandatory rewrite follows from this library.

## Contract handoff and completion

Record entity/field, authoritative owner, stable identity, input/derived/default/override/snapshot status, writers, readers, projections, invalidation and tests where affected; [service contract](templates/service-contract.md) supplies a format when needed. An item override wins over a project default when that is the adopted model; explicit historical snapshots are a separate policy. A request DTO, cache row, export and UI badge expose projections, not competing truth. If a fact cannot be traced to an owner, report the unresolved ownership instead of selecting the most convenient field.

The minimal delta is: task and authorized scope; inspected revision; existing contract; changed behavior; canonical owner; impacted layers/files; rule applicability; decisions; concrete assertions; evidence and limitations. Name a GoF pattern only when it solves a visible variation or boundary. Simple composition is the default, not an exception needing a design essay.

Specification is complete when its resolved contracts and dependent unknowns are explicit. Implementation is complete only for the verified scope, with required mutation paths and consumers accounted for. Verification is complete when the report is reproducible and honest, even if runtime assertions remain unverified. Do not equate source construction, test execution, deployment and business acceptance.

Shared frontend/backend concerns belong in the project: stable error codes and field paths, business status meanings, idempotency/conflict outcomes, operation polling and access-loss behavior. Backend work must not independently invent UI recovery, and frontend work must not invent server guarantees. An accepted HTTP response is not necessarily durable business success. Agreement about those meanings is part of the handoff, not an optional polish step.
