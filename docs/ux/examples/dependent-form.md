# Worked example: dependent form, remote check, rejection and recovery

Illustrative contract EX-FORM, revision 1. Every product/API/foundation value here is a **fictional resolved assumption**, not an approved business rule for a consuming project. Behavioural execution: NOT VERIFIED. This example deliberately resolves its policies so that an implementer can follow the trace without filling hidden gaps.

## Task and authority assumptions

Create a shortcut in a chosen workspace folder. Fields: Workspace, Folder and Name. Fixture schema EX-SCHEMA-1: workspace IDs A or B; folders A1/A2 belong to A and B1 to B. IDs are synthetic; no ownership is inferred from labels. Name is required, 1-40 Unicode code points after trimming leading/trailing whitespace; interior whitespace/case/diacritics preserved. Those bounds exist only in the fictional service schema. Server independently validates membership, length, permission and uniqueness of `(workspaceId, folderId, normalisedName)`.

Fixture availability service is advisory, checks exact case-sensitive tuple, and returns available/taken; transport failure means no evidence. Check on Name blur when all applicable local rules pass, or on Submit when no current evidence exists. Input changes clear dependent remote evidence immediately; local revalidation occurs during correction, remote recheck waits for blur/Submit. No debounce. Check timeout = 5 seconds in the fixture. A completed check is evidence only for that tuple/revision; it reserves nothing. Submit can proceed after a current check passes or is unavailable, because server remains authoritative; while checking, it sends no mutation and asks for another Submit after resolution. It never auto-submits.

Fixture create API accepts a client operation ID, atomically commits or returns a documented non-committing validation rejection. An authenticated lookup by operation ID returns pending/committed/rejected/unknown; this is a fictional provided capability, not invented for real APIs. No guarantee of repeat-write idempotency is assumed: an unknown outcome is looked up, never automatically repeated. Canonical create result owns new shortcut ID. Shortcut list refreshes from that result/server; no optimistic insertion. Other consumers: none in this fictional scope.

## EF-FORM-1 and BASE-FORM-1

EF-FORM-1: native labelled selects, text input, buttons; fieldset/legend for destination; inline error under field; linked error summary above form. Typography 16px/1.5 system UI, heading 20px/1.4; spacing 8/16 CSS px; white surface, #111111 text, #454545 hint, #8B0000 error; 3px #005FCC focus outline/2px offset; control min-height 44px; radius 4px; no shadows or animations. Labels/help/errors wrap; 40-code-point value remains editable via native input scrolling. Single column at 320/768/1280 CSS px; no sticky elements/overlay/nested scrolling. en-GB, left-to-right; no date/units in this form. Proposed test target for example only: WCAG 2.2 AA, Chrome/NVDA, keyboard/touch, 200% text size and 320px reflow. No rendered measurement is claimed.

BASE-FORM-1 supplies all F-* and V-* records below: state owner = form controller for action; field validation owner = schema/form controller; authoritative data = service. Read request key includes actor, permission revision, workspace, folder, normalised name, form revision and a monotonically increasing request generation. A timed-out read retires its generation, so a late reply is ignored even if the tuple is unchanged. Local edits increment revision; accepted action result uses the submitted immutable revision and operation ID. Identity/access change clears restricted input/evidence, invalidates view responses and enters F-ACCESS; never restores another account's form.

Inputs persist in memory through checks and confirmed rejection; no draft persistence. Refresh/close loses draft with visible note `This draft is kept only while this form is open.` App-controlled Cancel discards after explicit `Discard this shortcut draft?` if dirty; choosing Keep editing returns to form. Browser close cannot be guaranteed interceptable; no recovery promise is made. Operation ID only (non-secret opaque ID, no name/folder text) is session-stored under actor for lookup after interrupted submit; clear on confirmed terminal outcome/logout/tab close. This limited retention is an illustrative privacy approval.

One polite status region announces accepted check/action messages once; field error text is associated using described-by/invalid semantics. Ordinary blur/input/check completion does not move focus. Unsuccessful submission focuses summary; links move to labelled error fields. Error summary lists only current applicable errors in Workspace, Folder, Name order. Successful create focuses success heading. All actions have keyboard/native semantics; Enter in an active IME composition commits text only, not the form. No animation/timer dismissal. Abort read transport on disposal where supported; always invalidate callbacks. A dispatched write is tracked by operation ID and is never described as cancelled just because view disappeared.

All F-* and V-* states explicitly inherit BASE-FORM-1 and EF-FORM-1. Applicability = this example; strength = CONDITIONAL; source/status = ILLUSTRATIVE ASSUMPTION; rationale = truthful correction and independent evidence; exceptions = none; dependencies = EX-SCHEMA-1 and fixture services; acceptance tests FX below, all NOT VERIFIED. Unknown/terminal navigation behaviours are overridden in action table.

## Field contracts (inherit BASE-FORM-1)

Feedback profile is deliberately **INTERACTIVE**; submission policy is deliberately **enabled Submit that reveals errors without sending an invalid mutation**. Both are resolved only for this example. Error priority is prerequisite membership/required, then local bounds, then current remote/server rejection. Warnings do not block. There is one custom form error presentation using native controls; competing browser validation popups are disabled in the example implementation contract, while semantics remain.

| Field | Authority, accepted values, normalisation and dependencies | Check / feedback / pending | Copy, clearing, preservation and responsibilities |
|---|---|---|---|
| Workspace | EX-SCHEMA-1; required A/B; identity unchanged | Local on change; feedback on blur/submit, revalidate correction | Label `Workspace`; empty error `Choose a workspace.` Change clears Folder and remote Name evidence; preserves Name draft. Server checks permission/membership |
| Folder | EX-SCHEMA-1; required when Workspace chosen; exact A1/A2 or B1 membership | Disabled before workspace with visible `Choose a workspace first.` Inapplicable field doesn't validate/serialize; local on change, present blur/submit | Label `Folder`; applicable missing error `Choose a folder.` Invalid membership `Choose a folder in this workspace.` Changing Workspace clears value/error and hides dependent Name rejection; server validates relationship |
| Name | EX-SCHEMA-1; required; 1-40 code points trimmed at edges only; uniqueness depends on all fields | Local on completed input/blur/submit; exposed errors revalidate on completed input; remote rules above; pending doesn't claim valid | Label `Name`; hint `Use 1–40 characters. Availability is checked for the selected folder.` Empty `Enter a name.` Bounds `Use no more than 40 characters.` Taken `This name is already used in this folder. Choose another name.` Clear local error only when rule passes; tuple change clears obsolete remote/server Name rejection to local-pass/unverified; preserve allowed text |

Server rejection with no safe field mapping stays at form summary with `We couldn't create the shortcut. Review the message and try again.` A service-specific reason must be mapped from documented safe codes, not raw text. Name-taken rejection is mapped only to Name for the submitted tuple. Client prechecks never replace server enforcement/authorization.

## Validation axis

| State | Meaning/nature/entry (all are non-mutating evidence) | Presentation and actions | Exit / forbidden transition | Fixture |
|---|---|---|---|---|
| V-UNTOUCHED | No user feedback trigger; excludes local pass | Requirements/hints, no error; edit/Submit allowed | Blur/submit evaluates applicable fields; never show imported invalid data as untouched | FX1 |
| V-INCOMPLETE | Required information absent; known local failure after feedback trigger | Exact required message inline; correct or Submit to reveal all; no mutation | Passing required rule -> local evaluation; focus alone cannot clear | FX2 |
| V-INVALID | Membership/bounds failure; known local failure | Exact ordered field error; edit available, mutation guarded | Correct -> V-LOCAL if all local rules pass; no timer clear | FX3 |
| V-LOCAL | Current local rules passed; excludes remote acceptance/ownership | Hints only; no green verified badge; blur/Submit starts check when applicable | Start -> V-CHECKING; input re-evaluates and invalidates remote evidence | FX4 |
| V-CHECKING | Current tuple read pending; remote truth unknown; 5s timeout | `Checking name availability…` under Name; editing/Cancel allowed if no write; Submit announces `Wait for the name check, then submit again.` and sends nothing | Current reply -> V-CHECKED/V-REJECTED; timeout -> V-UNAVAILABLE; tuple edit -> local state; obsolete reply is no-op | FX5/FX8 |
| V-CHECKED | Current service replied available; not reservation/final acceptance | `Name was available when checked. It will be checked again when you create.`; Submit available | Submit -> F-SUBMITTING if local rules still pass; edit clears evidence; no direct success transition | FX6 |
| V-REJECTED | Current tuple confirmed taken, from check or documented non-committing server rejection | Exact taken error; edit available; Submit reveals it but sends no same-tuple mutation | Change tuple -> local state and obsolete error clears; no error clearing merely on unrelated edit | FX6/FX7 |
| V-UNAVAILABLE | Check failed/timed out; remote answer unknown; not taken | `We couldn't check this name. You can still submit; the server will check it.`; Submit/edit available, blur can retry check | Submit -> F-SUBMITTING with valid local input; new check -> V-CHECKING; no invented remote rejection | FX9 |

Warning/imported review states are NOT APPLICABLE in this create-only fixture; consuming edit/import flows must resolve them separately. Every V state uses the base focus/announcement/storage/layout policy; current error/pending text is persistent until its stated transition. The form-level dirty flag is independent of V state.

## Action axis

| State | Meaning/nature/entry | Presentation, restrictions and preservation | Transitions / timing / forbidden targets | Fixture |
|---|---|---|---|---|
| F-EDITING | Write not dispatched; validation axis independent; current draft editable | Form/Submit/Cancel; Submit either shows summary, begins/waits for check, or dispatches exactly one locally valid current revision | Guarded submission -> F-SUBMITTING; Cancel per base -> disposed; never infer committed from local/check pass | FX1-FX5 |
| F-SUBMITTING | Write dispatched for frozen revision; commit not known | `Creating shortcut…`; fields read-only/disabled as native control supports, Submit/Cancel guarded with visible `Creation is in progress.`; focus retained | Response confirmed commit -> F-SUCCESS; documented rejection -> F-REJECTED; lost response/10s fixture timeout -> F-UNKNOWN; browser leave cannot cancel server | FX6/FX10 |
| F-REJECTED | Server confirms no commit; recoverable correction | Restore editability and permitted values; mapped Name error plus focused summary `Shortcut wasn't created. Correct the error below.`; Submit remains available for validation | Correct implicated tuple -> F-EDITING and V-LOCAL; current rejection can't become success merely on field edit | FX6/FX7 |
| F-UNKNOWN | Write may have committed; reconciliation required | `We couldn't confirm whether the shortcut was created.`; persistent `Check outcome` and `Leave` actions; new create disabled with visible reason; draft retained in memory | Check outcome -> F-RECONCILING. Leave allowed, operation ID retained for lookup on return; no repeat write | FX10 |
| F-RECONCILING | Read lookup pending for operation ID; write outcome still unknown | `Checking creation outcome…`; Check outcome guarded, Leave available; new create remains disabled; permitted draft retained | Latest lookup committed -> F-SUCCESS; rejected -> F-REJECTED; pending/unknown/error/5s timeout -> F-UNKNOWN with persistent `Creation is still unconfirmed. Check again later.` Retire read generation on timeout; never interpret timeout as write failure | FX10 |
| F-SUCCESS | Canonical create response/lookup confirms commit | Heading `Shortcut created.` and `View shortcut` link using returned ID; form draft/errors cleared, operation ID removed | Link navigates to canonical item; no expiry/toast-only success; subsequent independent create requires new action | FX7/FX10 |
| F-ACCESS | Actor/permission context invalidated; no authorised form data; write certainty unchanged | Heading `Access changed.`; `Sign in again to continue.` and link to fictional existing `/sign-in` route; focus heading if removed form held focus; form/Submit absent | Invalidate all view callbacks and clear restricted draft/check evidence. Same actor authorised return with retained operation ID -> F-RECONCILING; no pending operation -> fresh F-EDITING. Confirmed logout clears stored ID; never restore another actor's data | FX8/FX10 access variant |

Access revocation from any state enters F-ACCESS; pending operation must be reconciled only after the same actor regains authorised access. The fictional `/sign-in` route and canonical item route `/shortcuts/{returnedId}` are fixture assumptions, not newly requested product features. No response for a previous actor restores form content. Dispose aborts read callbacks; action certainty remains what the service last proved. All action states preserve independent surrounding navigation except the explicitly guarded form Cancel during submission; browser-level navigation is never assumed preventable. Leaving via F-UNKNOWN/F-RECONCILING returns to the fictional shortcut list route `/shortcuts` and explicitly states `Creation is still unconfirmed. Return to check its outcome.`

## Reproducible recovery and race tests

All tests below are planned assertions, NOT VERIFIED executions.

- **FX1-FX3:** untouched has hints/no errors; Submit empty exposes Workspace and Name, not inapplicable Folder; select A exposes required Folder; 41-code-point Name fails, 40 passes local bound; corrections clear only passed rules. Paste/autofill/IME and leading/trailing whitespace obey EX-SCHEMA-1.
- **FX4-FX5:** select A/A1, Name `Daily`; blur starts check C1. Submit while held sends no create. Changing Folder A2 clears remote evidence. Changing Workspace B clears Folder, preserves Name and excludes inapplicable Folder until a new selection.
- **FX6-FX7:** C2 for A/A1/`Daily` returns available. Submit dispatches frozen revision R2; fixture server returns non-committing name-taken (another actor won). Summary focuses, values persist and Name associates taken error. Change to `Weekly`: obsolete rejection clears to local-only evidence; blur C3 passes; Submit R3 commits ID S1. Success heading focuses, operation ID/draft clear, canonical list includes S1 once.
- **FX8:** start C4 for `Daily`, change to `Weekly`, start C5; deliver C5 available, then C4 taken. Neither current message, focus nor announcements may change on C4. Repeat with dependency change and access revocation.
- **FX9:** time out current check; label unavailable, not taken. Locally valid Submit is allowed under this explicit advisory-check policy; real server remains the final validator.
- **FX10:** server commits R4 but reply is dropped; 10s fixture timeout enters unknown, never failure. Duplicate Submit blocked; lookup returns committed S2; success/list show S2 once. Repeat lookup pending, outage and confirmed rejection; no repeat write occurs. Reload restores only actor-scoped operation lookup, not draft values.
