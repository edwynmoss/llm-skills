# Data states, actions and recovery

Inherit RULE-BASE from [governance](../governance.md). Each applicable feature state is instantiated with [the state template](../templates/state-contract.md). This catalogue defines meanings, not ready-to-build product states: no anatomy/token/timing value may be inferred from a label alone.

| ID | Applicability / strength | Authority/status; rationale | Expected behaviour | Exceptions / dependencies | Observable acceptance |
|---|---|---|---|---|---|
| STATE-01 | State-bearing feature; MUST | U4C/U5; USER REQUIREMENT; labels are insufficient | Give each applicable state identity, nature, owner, revision, presentation, actions, preservation, time, access, concurrency, transitions and evidence. Keep content/action/validation axes separate; enumerate meaningful combinations | Inherit only a named concrete definition; unresolved values block dependent implementation | Implementer can reproduce state and next transition without choosing undocumented UX policy |
| STATE-02 | Async region/action; MUST | U4C; USER REQUIREMENT; minimum useful scope | Preserve authorised unaffected content and independent interaction. Place feedback at field/action/region that owns it. Use persistent important errors and useful recovery; show elapsed/progress only from real observations | Access loss takes precedence; D15 freshness tolerance | Failing one panel leaves independent controls operable; error survives until correction/recovery; no invented percent/stages |
| STATE-03 | Concurrent work; MUST | U5/U6; USER REQUIREMENT; obsolete results corrupt truth | Associate result with entity, identity/permission context, request generation, input/dependency revision and authoritative version as relevant. Ignore obsolete responses. Prioritise access revocation over cached content, then scoped lifecycle locks; do not let refresh status erase write outcome | No universal total ordering: independent axes coexist; D02/D05 | Old success cannot clear new error or restore forbidden data; invalidated responses cause no announcements/focus change |
| STATE-04 | Write/action; MUST | U4C; USER REQUIREMENT; transport is not commit certainty | Define one submission path, pending guard, authoritative success/rejection, unknown outcome and reconciliation. No repeat of an uncertain write without verified safety; cancellation request is not confirmed rollback. Optimism records reversible projection and canonical reconciliation | D05; absence of reconciliation support must be exposed, not invented | Drop response after server commit: UI never asserts failure or sends duplicate automatically; confirmed success updates consumers |
| STATE-05 | Shared/concurrent records; CONDITIONAL | PROPOSED; user can overwrite another valid edit | Bind edits to record version when supported; surface conflict with changed context. Resolve compare/reload/merge policy through domain owner; preserve permitted draft separately from server record | D06; do not implement a merge engine or assume last-write-wins | Two actors edit same record; older revision cannot silently overwrite under conflict policy; chosen resolution reaches all consumers |
| STATE-06 | Draft/cache retention; PRODUCT DECISION REQUIRED | U5 + PROPOSED extension; privacy and recovery | Record owner, storage, lifetime, identity key, reload/close/logout/access-loss clearing and permitted restoration. Do not introduce persistence merely for convenience | D07/D08; security restrictions override preservation | Account switch/revocation removes restricted projections and storage; permitted draft restores only in correct context |
| STATE-07 | Resume/offline/rate limit; CONDITIONAL | PROPOSED; resumed timers and connectivity are unreliable | Treat connectivity as observation, not proof of service availability. On resume re-check relevant freshness/authority. Respect documented retry signals and bounded policy; no automatic write queue or replay without contract | D05/D15; only workflows affected by interruption | Suspend/reconnect/backoff simulation never duplicates action or labels stale data current; recovery remains available |

## Meaning catalogue (STATE-01 specialisations to instantiate)

| State kind | Meaning / excludes | Nature and typical entry | Required distinction in contract |
|---|---|---|---|
| Initial loading | No usable result for current key; not empty | Read pending, certainty unknown, region blocked | Content placeholder versus text, useful escape, timeout and terminal path |
| Background refresh | Usable permitted snapshot exists while read runs | Read pending, content freshness known from last evidence | Snapshot age/copy, actions safe on stale data, refresh failure |
| Incremental loading | Additional segment requested | Read pending for cursor/page; previous segments available | Cursor identity, duplicate rows, end-of-list versus failed segment |
| Available | Result confirmed for current key/version | Read complete; freshness tied to observation | Does not mean every future write will succeed |
| Partial availability | Some declared dependencies/segments missing | Mixed read certainty; only dependent scope blocked | Missing portions, totals limitations, safe remaining actions |
| Stale | Freshness contract no longer met | Read snapshot known but current truth uncertain | Not necessarily error; whether use is safe is D15 |
| First-use empty | Authoritative no records, onboarding task relevant | Confirmed read with zero records | No invented invitation/create capability |
| No results | Applied query yields zero matches | Confirmed for query revision | Preserve draft/applied query; adjust/clear filters if supported |
| Goal-completed empty | Work queue actually exhausted by task success | Confirmed domain state | Distinguish filtered-out work or failed request |
| Read failure | Request failed; may have snapshot or no content | Confirmed read failure, recovery depends on cause | Not proof underlying collection is empty |
| Submitting | Write dispatched but terminal outcome absent | Write pending; certainty unknown, action guarded | Navigation, duplicate activation, cancellation, revision |
| Confirmed rejection | Authoritative response says not accepted/committed under API contract | Write not committed as documented; correct/retry only where allowed | Preserve allowed input; identify checked revision and reason safely |
| Confirmed success | Authority confirms intended operation/result | Write committed; downstream sync may still be pending | Do not call UI optimistic projection confirmed success |
| Unknown outcome | Commit could have occurred; evidence insufficient | Write uncertain; reconcile before unsafe repetition | Persistent uncertainty copy, lookup/support path if available |

Empty states require authoritative successful retrieval for the current key. A 403, timeout or parser failure is not empty. An error's copy states only known facts: e.g. `We couldn't refresh {region}. Showing data from {time}.` An uncertain write says `We couldn't confirm whether {action} completed.` Add only verified recovery options. Never include raw server stack traces or unverified causes such as “Your internet is down.”

Transition rows contain event, guard, side effect, target and forbidden target. Request cancellation for cleanup and ignoring stale results are separate responsibilities. Unmount invalidates view callbacks; it does not prove a server write stopped. Define whether a parent owner continues tracking the operation.
