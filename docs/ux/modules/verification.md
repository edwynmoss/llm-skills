# Verification and bounded automation

Inherit RULE-BASE from [governance](../governance.md). [Acceptance template](../templates/acceptance.md) is the evidence ledger. Evidence statuses have precise meanings: VERIFIED = the stated assertion was observed in the stated environment/revision; FAILED = observed mismatch; NOT VERIFIED = unexecuted, blocked or insufficient evidence; NOT APPLICABLE = excluded with a predicate-based reason. A static review verifies only static properties.

## Bounded read-only review

For requests such as "try this against our codebase; no changes", start with ui-verify and report inline. Confirm repository identity, revision, existing edits and local contracts. Select one representative existing flow when the user asks for a pilot without naming one; state the choice and exclusions. Do not install the skill into the target repository merely to read and apply it. Trace only relevant owners, callees, consumers and tests; expand scope when evidence requires it.

Use existing commands only after checking their side effects. A command called test or lint can still restore packages, generate files, rewrite snapshots, seed data or contact a live service. Use a documented non-mutating invocation where available; otherwise leave that check unexecuted and explain why. Do not silently run setup, start an application, enable hooks, change baselines, create issues or repair the code. Existing previews can support authorised read-only observations; interactive tests that mutate state need an appropriately authorised fixture. A separately requested isolated test run may use disposable artifacts within that scope.

Record command, exit status, tested scope and output meaning. Compare end state to the starting state using Git status/diffs and targeted content hashes where useful. State coverage: Git status alone does not prove file contents or ignored outputs unchanged. Large whole-tree hashes are not a mandatory ritual. If concurrent work changes the tree, report that limitation; do not restore another actor's edits. Finish with findings, useful existing strengths and unverified assertions, rather than requiring an app launch to complete the report.

## Evidence basis and finding format

Evidence basis is independent of VERIFIED/FAILED/NOT VERIFIED/NOT APPLICABLE; it does not add a second status taxonomy.

| Basis | What may be claimed | What remains separate |
|---|---|---|
| Source observation | Exact branch, mapping, owner or missing guard in inspected source at a revision; trace callees/shared behaviour before declaring a gap | Whether the branch is reached, race schedule occurs or a user experiences the inferred effect |
| Executed check | What the named command or observed interaction actually asserted, with environment and result | A token scan does not establish computed contrast or keyboard behaviour; an existing baseline count is not a defect count |
| Runtime hypothesis | A plausible, explicitly conditional consequence with triggering sequence and a check that could refute it | Runtime assertion remains NOT VERIFIED until exercised; severity does not promote confidence |

Use one compact record per finding: `priority and consequence; local requirement or proposed improvement; source/revision; observed fact; inferred effect and preconditions; evidence basis/status; smallest confirmation or refutation; repair direction without implementation`. If one finding spans evidence types, split the assertions instead of labelling the entire finding "verified".

For example, source may establish that a failed read maps to an empty collection; it does not prove a particular user's session encountered that failure. A pending handler retaining old results plus an unguarded Enter path supports a stale-activation hypothesis; confirm event ordering in the actual framework before claiming a reproduced race. Before calling an ARIA pattern incomplete, inspect shared keyboard/focus infrastructure as well as local markup. A source test asserting an attribute exists is not evidence that the interaction works.

## Test failure attribution

After a failed check, record command/revision, exit result, failure location, setup completion and whether the intended assertion executed. Classify only as specifically as the evidence permits:

| Observed failure | Report meaning | Next bounded check |
|---|---|---|
| Intended assertion runs and differs from the approved contract | Assertion FAILED in that environment; inspect cause before assigning it to production code rather than an invalid fixture or expectation | Reproduce the relevant input/order and compare implementation, fixture and authoritative contract |
| Fixture, mock, runner or setup throws before the assertion | Executed command FAILED; dependent product assertion NOT VERIFIED | Compare the failing dependency's actual interface with the fixture; propose or, when authorised, repair the smallest mismatch and rerun the original check |
| Required environment, permission or dependency unavailable | Dependent assertion NOT VERIFIED; state the concrete blocker | Use another authorised evidence source or report the missing requirement; no automatic installation or live-data fallback |
| Cause cannot yet be distinguished | Preserve raw result and mark attribution unresolved | Identify the smallest check separating competing explanations; do not force a product-defect label |

A test double missing a real platform method does not establish that the platform implementation is broken. Do not weaken a production guard, remove an assertion or rewrite expected behaviour just to obtain green output. A repaired fixture still needs the original assertion exercised. In a read-only review, propose that repair without editing. Passing doubles remain supplementary evidence for real-boundary claims under VERIFY-02. These failure categories describe evidence, not additional status values.

## General behavioural probes and positive controls

Reuse existing state rules; select these probes only when the feature has the relevant behaviour. Use deterministic response order in an authorised fixture, not sleeps or repeated actions against live records.

| Relevant contract | Observable probe | Correct implementation to recognise |
|---|---|---|
| Read failure, empty result and successful recovery | Deliver failure, then a successful empty response, then a successful nonempty response. Assert distinct truthful feedback and preserved permitted input/context | A discriminated read state prevents failure from displaying success-empty copy; no extra state manager is necessary |
| Repeated mutation and derived UI projection | Deliver two successful acknowledgements for the same logical transition. Check the item, aggregate and reload against the authoritative owner; do not assume the API is idempotent | Existing deduplication, transition guards or canonical reconciliation may already preserve the invariant; a new store or mutation layer is not required |
| Optional action target with a supported fallback | Omit the optional target; activate the fallback with each supported input method and check its accessible name and destination | A native focusable control or framework equivalent exposes the fallback; custom keyboard handling is unnecessary when native semantics suffice |
| Component extraction, styling or theme change | Run the applicable component/token checks below and compare with the approved baseline | Stable identity, sensible local composition, legitimate runtime geometry and existing role tokens are valid; syntax alone is not a defect |

Record existing safeguards as source observations or executed assertions with the same precision as defects. Test broken and correct variants during skill evaluation so that adding findings is not rewarded at the expense of accuracy. Evaluation procedures and fixtures belong in [the evaluation catalogue](../evaluations.md), not in every product task. A rendered accessibility pass combines applicable automated checks with keyboard, focus, naming, announcement, reflow and supported AT observations; unavailable parts stay NOT VERIFIED. Tools alone cannot establish conformance ([W3C evaluation guidance](https://www.w3.org/WAI/test-evaluate/)).

## Targeted component and token verification

When CAP-06/CAP-07 or VIS-07 through VIS-09 apply, inspect actual component boundaries and token definitions, then exercise the affected rendered behaviour. Do not equate a lint pass, a count of extracted files or a grep for hex colours with architectural correctness. Use the component/token ownership tables in [state contract](../templates/state-contract.md) and [acceptance](../templates/acceptance.md).

Required applicable assertions: parent rerender preserves edited values and focus; intentional identity changes reset only the named state; selected variants preserve correct semantics; token aliases resolve to the approved owner; role-specific contrast/focus survives supported themes and states; legitimate runtime geometry still changes; a shared-token edit reaches all affected consumers. Existing linters/theme tooling may supplement these checks. No new blanket inline-style or arbitrary-value ban is authorised by this package.

VERIFY-06 extends evaluation using [moderated usability testing guidance](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing) and [completion measurement guidance](https://www.gov.uk/service-manual/measuring-success/measuring-completion-rate). These sources describe service-design methods; their government-specific reporting obligations are not imported. A small formative session supports observed findings, not a statistically reliable population success rate. Benchmarks, telemetry and human research require an actual project scope and appropriate consent/permissions.

## Adopted package hooks and future project automation

Revision 1.6 adopts optional advisory SessionStart library health and PostToolUse package integrity checks after explicit implementation authorization. The [hook operations guide](../hooks.md) owns installation, scope, trust, bounds and removal. These checks run only against the shared skill source/installation; they do not certify application behaviour. The context installer still does not activate hooks.

A possible later extension is a consuming repository's existing deterministic contract-reference, component or token check on relevant changes. Proposal fields: manual command/version; known pass/fail fixtures and measured duration; file allowlist; exact supported event/matcher; owner; timeout and output limit; no network/install/recursive agent invocation; per-session/change fingerprint; skip re-entry; only one bounded continuation if Stop is used; actionable file/rule failure; explicit handling of tool failure/timeouts as NOT VERIFIED; independent CI command; removal/revisit conditions. Log no transcript or secret input. Execution limits must be measured for the actual check, not copied as arbitrary constants.

Manual/CI runs must remain available if hooks never run. Do not convert missing hook output into a pass. No consuming-project check or Stop hook is adopted yet; the general skill must not invent platform-specific enforcement or infer validation from assistant prose.
