# Conditional human-AI interaction contracts

Read this module only when the product feature exposes generated suggestions, extraction, predictions or AI-triggered actions. Using an AI coding assistant to build an ordinary form does not activate it. Inherit RULE-BASE from [governance](../governance.md); canonical ownership, action certainty and privacy remain in their existing modules.

| ID | Applicability / strength | Authority/status; rationale | Expected behaviour | Exceptions / dependencies | Observable acceptance |
|---|---|---|---|---|---|
| AI-01 | User-facing generated/extracted/predicted information; CONDITIONAL | U9; APPROVED AUTHORING POLICY informed by S7; plausible output is not verified truth | Define capability and known limits in task language. Distinguish generated suggestion, source-supported extraction, user-reviewed value, independently verified fact and committed record. Preserve relevant source evidence and route accepted values through canonical validation; never imply user review proves factual accuracy | D21/D02/D11; provenance is not a correctness guarantee. Display confidence only with a documented interpretation/calibration; no invented percentages | Deliberately plausible wrong output stays distinguishable from confirmed truth; accepting it does not bypass domain validation; source absence/contradiction remains visible |
| AI-02 | User reviews or corrects AI output; CONDITIONAL | U9; APPROVED AUTHORING POLICY informed by S7; efficient correction preserves user control | Specify invoke, dismiss, edit, accept and retry controls that actually exist. Preserve user edits across regeneration, or explicitly resolve replacement/merge behaviour. Bind generated responses to input/context revision; require a decision for consequential ambiguous matches | D21/D07; existing state/cancellation rules apply. Do not add feedback collection or store sensitive prompts by default | User can reject or correct a wrong suggestion; late/regenerated output cannot overwrite edits or silently match an ambiguous entity; unavailable AI leaves the defined fallback usable |
| AI-03 | AI can cause an external or canonical mutation; CONDITIONAL | U9/A; USER REQUIREMENT for authority, APPROVED AUTHORING POLICY for interaction | Separate proposal, authorisation, dispatch, pending, confirmed and unknown outcome. Resolve action scope and review/approval boundary proportional to consequences; disclose affected entities before commitment where required. Use the same authorised canonical use case as manual input | D21/D05; no blanket confirmation for harmless actions, no assumed execution permission or new automation. STATE-04 owns write certainty and retries | A generated plan cannot masquerade as an executed action; interrupted execution is reconciled without unsafe repeat; manual/AI paths preserve the same validation, lifecycle and downstream outputs |

The research basis is [Amershi et al., Guidelines for Human-AI Interaction, CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf), which evaluated general interaction guidance. These rules adapt that guidance to this package's canonical-state requirements; the paper does not validate this package or any particular modern model.

Instantiate actual AI-specific states with the [state template](../templates/state-contract.md), extending the content/action axes rather than creating a competing business status. Source identity, checked revision, user-edit ownership and verification basis must be explicit. Minimum adversarial scenarios: plausible incorrect suggestion, absent/conflicting source, ambiguous entity match, stale generated reply after edit, interrupted operation and successful user correction. Tests are project-scoped; no model/API calls are required merely to read or author this module.
