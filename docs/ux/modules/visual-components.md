# Visual foundations and component contracts

Inherit RULE-BASE from [governance](../governance.md). The semantic names below describe slots to map, not a newly imposed token system. Never claim a component is approved merely because this file names its category.

| ID | Applicability / strength | Authority/status; rationale | Expected behaviour | Exceptions / dependencies | Observable acceptance |
|---|---|---|---|---|---|
| VIS-01 | Product-wide/new styling; MUST | U4B; USER REQUIREMENT; one visual foundation | Resolve D03: approved reference and existing token/component paths for type scale, semantic colour, spacing, density, sizing, surface/elevation, radius, themes, icons and content. Map state slots to them | Small existing-component change inherits named foundation; no forced ideation | Same semantic state uses same approved token/component; light/dark and text extremes inspected |
| VIS-02 | Interactive component; MUST | U4B; USER REQUIREMENT; avoid misleading semantics | Specify purpose, anatomy, accessible name, value/state, label/help/error/action placement and component API. Navigation uses links; operations use buttons; value selection uses selection controls, not action menus | Native/selected library mechanisms first; W2 is informative pattern guidance | Keyboard and screen reader expose the intended action/value, and visible label matches accessible name |
| VIS-03 | Reachable state combinations; MUST | U4B/U5; USER REQUIREMENT; state axes are independent | Inventory resting, hover, focus-visible, pressed, selected, checked, indeterminate, expanded, dragging, disabled, read-only and busy where meaningful. Define reachable combinations and exclusions. Selected+read-only still communicates selected; focus+busy retains a perceivable location | Product determines editability; disabled is not read-only; drag only when present | Reproduce each meaningful combination and assert semantics, contrast, action guards and focus, not CSS alone |
| VIS-04 | Overlay/popover/dialog; CONDITIONAL | U4B; USER REQUIREMENT; focus ownership | Name opener, initial focus, modal/non-modal scope, dismissal paths, pending/dirty guard and focus return. Use one library's stacking/focus system. Nested overlay closes its own layer first; if opener disappeared, use named logical fallback | Never add a second focus trap atop library. Escape/overlay-click policy depends on task and library contract | Keyboard reaches every control without escaping an intended modal; dismissal returns to visible fallback; underlying content behaves per modality |
| VIS-05 | Responsive/overflow layout; MUST | U4B/F; USER REQUIREMENT; avoid screenshot-only responsiveness | Record transformations at content-driven widths: wrap/stack/reorder, table overflow, toolbar priorities, sticky boundaries and nested scroll ownership. Essential data/actions must remain reachable. Test intermediate widths, virtual keyboard and zoom | True two-dimensional data may scroll with headers/context retained; D04 | No hidden actionable content or clipped error; focus scrolls into view without being obscured |
| VIS-06 | Motion/progression; CONDITIONAL | U4B/F; USER REQUIREMENT; change must remain understandable | Specify motion purpose, trigger and end state. Reduced-motion alternative uses immediate state change or non-motion cue; no essential information exists only in animation | Do not fabricate progress; STATE-02 | Reduced-motion preference still reveals status and next action; transitions do not move controls under activation |
| VIS-07 | Component styling; MUST | U9/A; USER REQUIREMENT; semantic ownership prevents visual drift | Inspect the actual token source and consuming component API. Consume approved roles for text, surface, border, action, focus and status; reuse approved scales for spacing, type, size, radius, elevation and motion. Keep raw design values in their owning foundation. Resolve aliases to that source; do not invent feature palettes, duplicate token files or choose a raw palette colour by appearance | Follow existing token tiers/names/tooling; do not require a new primitive/semantic/component tier. Token absence is D03, not permission for an invented global foundation | Trace affected styled properties to approved definitions; no unexplained hard-coded design values or competing role tokens; missing/broken/cyclic aliases are surfaced |
| VIS-08 | State/theme/token changes; MUST | U9; USER REQUIREMENT; a token name alone does not establish correct rendering | Record component variant/state-to-token mapping and supported themes/modes. Change the authoritative token or component variant at its owner; trace shared consumers before changing broad tokens. Verify meaningful state combinations, contrast, focus and system high-contrast behaviour where supported | D03/D04 determine themes, density, forced-colours and platform handling; preserve library mechanisms and resolved exceptions | Light/dark or other supported modes retain semantic meaning and operability; shared-token change has evidence for affected consumers, not just one screenshot |
| VIS-09 | Inline styles or untokenised values; DEFAULT WITH OVERRIDE | U9; APPROVED AUTHORING POLICY; distinguish design decisions from runtime data | Use project styling conventions and approved variants for design choices. Permit validated runtime quantities such as measured position, drag transform or actual progress via the library/framework mechanism or scoped custom property. Keep static design decisions tokenised; record necessary exceptions with scope, reason and verification | Native reset/layout constants, library internals, third-party boundaries and data-derived values may be legitimate; no blanket ban on style attributes or arbitrary-value syntax. No token for every number | Review raw values by meaning, not regex alone; runtime width changes correctly while colour/spacing/focus remain governed; no invented progress or unsafe raw CSS interpolation |

## Selection guide (details of VIS-02, not separate policies)

| Component family | Resolve before use | Avoid / evaluate |
|---|---|---|
| Button/link | Operation versus destination; normal, destructive or toggle semantics | Do not imitate links with click-only text; test native open-in-new-tab behaviour for navigation |
| Checkbox/radio/switch | Independent choices versus one-of-many; mixed selection meaning; immediate versus submitted effect | Switch is not a generic menu; indeterminate does not mean unknown server truth |
| Action menu | Actions on a named object; selected library's focus/arrow-key model | Do not use for mutually exclusive field input without intended selection semantics |
| Dialog | Whether interruption/modal focus is necessary; title, description, body, actions | Avoid nested modal workflows when in-page composition suffices |
| Tabs | Same-context panels, selected tab, focus versus activation behaviour | If panel fetch has latency, resolve manual activation; no tabs for unrelated destinations disguised as state |
| Combobox | Editable versus select-only, filtering, free text allowed or not, option identity, empty/checking states | Do not invent keyboard selection logic around a library widget; preserve typed text on no results |
| List/table | Reading versus comparison; row identity, headers, sort meaning, selection scope | A data table is not automatically an interactive grid; virtualisation must preserve navigation and counts |

For each selected component, add its documented library version/API and relevant [APG pattern](https://www.w3.org/WAI/ARIA/apg/patterns/) as references in the feature contract. The guide does not promise any library passes accessibility automatically.

## Applying token ownership

VIS-07 through VIS-09 apply to CSS variables, utility frameworks, CSS-in-JS, native platform themes and other project conventions. A utility class backed by an approved semantic token is still token use; an inline style referencing an approved token is not automatically a violation. Conversely, a variable named `error-red` does not prove approved ownership. Inspect its definition and consumers.

Use the role intended for the property: an error text role does not automatically provide the right contrast for an error background or border. Preserve state meaning independently of colour. Roles such as `text.error` are illustrative; reuse the project's actual equivalents. Carbon demonstrates role-based colour tokens and theme variation (source T1); this package does not prescribe Carbon or its naming. DTCG format/alias guidance (T2) is relevant only if token interchange/tooling needs it, not a required new dependency or file format.

When a token is genuinely missing, record the semantic purpose, existing candidates, affected components/modes, proposed owner and accessibility evidence. Use an existing approved role if it fits. Otherwise block only the dependent styling decision until resolved; do not silently add a global token, locally mask a broken alias or modify unrelated components. Record a targeted migration when deprecating/renaming a shared token.
