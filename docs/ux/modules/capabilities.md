# Packages, SDKs and application architecture

Inherit RULE-BASE from [governance](../governance.md). This module defines a selection process; no actual SDK/package recommendation is made without a project. Use [capability selection](../templates/capability-selection.md).

|---|---|---|---|---|---|
| CAP-01 | Capability implementation/gap; MUST | U4G; USER REQUIREMENT; avoid rebuilding solved systems | Inspect installed integrations first; compare suitable native/framework, existing, official SDK and established external options, including not-installed candidates. Verify required capabilities from current primary docs and exact runtime/version; evaluate maintenance, licence, accessibility, security and integration cost | No package installation in this authoring task. Future install follows task permission and package policy | Selection cites docs/version and satisfied/unsupported requirements; official/popular alone is not a justification |

A capability is suitable only if it supports the negative and recovery paths the feature needs, not just its success demo. Record unavailable documentation or inaccessible licence/security evidence as unresolved. Do not install or upgrade packages to investigate a speculative idea. A package-selection report can recommend a future change without claiming that it was installed or tested.

## What “no inline components” means here

Apply CAP-06 to responsibility, CAP-07 to component identity and VIS-09 in [visual standards](visual-components.md) to styling. These are separate checks. A page embedding an independent import workflow needs a clearer boundary; a simple paragraph does not need a new component/file. A React component type declared during another component's render is different from an ordinary event callback. Runtime geometry is different from a hard-coded design palette.

Follow existing semantic roles and naming: route/page composes; feature/section owns a meaningful capability; reusable component/primitive supplies a focused UI contract; hook/composable owns coherent UI state; domain/schema owns business validation; adapter/client owns provider access. These are responsibilities, not a required directory scaffold or obligation to create every layer. [Worked review](../examples/component-token-review.md) shows the distinctions without implementing an application.
