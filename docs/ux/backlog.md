# Phased adoption backlog

This is bounded follow-up work, not unfinished independent authoring or permission to implement an application now. Pick extensions only when an actual task requires them.

| Phase | Work / decision | Owner needed | Entry condition | Exit evidence |
|---|---|---|---|---|
| 1: Repository pilot | Adopt package tree; resolve D01-D04, D07-D09, D15-D18 as applicable; nominate maintainer | Product/design/domain/accessibility/tooling owners | A real existing read-only panel with independent surroundings and refresh already in scope | Discovery confirmed; existing foundation/role tokens mapped; scoped state contract approved; manual failure/recovery, focus and stale-response tests on actual UI/API; honest usability evidence status |
| 1: Component/token pilot | Apply small-change route and, where an existing defect exists, bounded component/token repair | Frontend/design-system owner | Actual requested label/style/boundary task; inspect existing components and token source | No unnecessary extraction; state/focus retained; role aliases and affected themes/consumers verified; missing-token decisions surfaced |
| 1: Authoring checks | Optionally run the target host's skill validator when available; this package supplies its own standard-library structural checks | Tooling owner | An available host validator and its documented runtime | Record host-validator results separately from this package's structural audit |
| 2: Skill behaviour | Execute unrun E01-E34 by risk; use E35-E37 as bounded correct/broken source controls, then test unseen examples and a matched prior-version comparison | Skill maintainer/evaluator | Appropriate fixture permissions and runtime/tool access | Actual prompts, routing, artifacts and rubric results; distinguish explicit invocation, automatic discovery and rendered behaviour; narrow corrections and affected reruns |
| 2: Mutation pilot | Pilot one existing dependent form; resolve D02/D05/D06/D10/D11 | Domain/API/product owners | Panel pilot useful and form is a real requested task | Real UI/API/database rejection, correction, out-of-order and successful recovery; unknown-outcome handling without duplicate writes |
| 3: Conditional workflow modules | Instantiate bulk/import/autosave/time contracts only where requested | Relevant workflow owner | Real workflow exposes corresponding risks | D12-D14 resolved as applicable; consumer/reconciliation and extreme-input evidence |
| 3: Conditional refinements | Instantiate resource-failure, support-handoff or AI interaction rules only where a real product requires them | Platform/support/product/domain owners | Actual feature or failure evidence activates relevant rule | D19-D21 resolved; real fallback/handoff/correction and canonical mutation evidence; no unrelated features added |
| 3: Application automation evaluation | Package-only advisory hooks are adopted in 1.6; separately measure consuming-project checks and any completion hook | Tooling owner | Repeated manual evidence supports the particular extension | D16 project decision with supported event/schema/runtime, recursion bound, independent CI and opt-out/removal plan; separate project activation authorization |
| Ongoing bounded maintenance | Update external references and affected rules when standards, runtime or real failures change | Named maintainer | Source/version change or demonstrated gap | Revision lineage, superseded evidence identified, affected tests rerun |

Use the [evaluation catalogue](evaluations.md) to choose independent small-change, unrelated-request and recovery controls. Record actual scope, artifacts, references, outcomes and limitations. Repeated-run reliability, automatic discovery and rendered user journeys remain separate from package checks. No new product features are needed solely to evaluate these skills.

Source coverage may be improved where the public register records limitations. Add platform extensions only for demonstrated needs. Hook installation and application changes require the user's actual task scope.
