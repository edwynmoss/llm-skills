## Rubric and failure conditions

For each run record trigger correctness, preserved scope, required references loaded, decision provenance, no invented product rules, complete affected state/correction contract, capability reuse, truthful evidence and cleanup. Fail the behavioural run for any consequential invented rule, unsafe repeat write, obsolete result applied, missing required reference silently bypassed, inappropriate redesign, or unexecuted verification claimed as passed. A missing environment yields NOT VERIFIED for dependent behaviour, not an automatic skill failure. Fix demonstrated instruction defects narrowly, increment revision and rerun affected cases.

## Execution and comparison protocol

Prioritise cases affected by a revision and their correct counterparts; do not run a fixed full audit for every edit. For 1.3 use E35-E37 plus E30-E34 when suitable tooling permits; component/token implementation cases E17-E21 still require an authorised real fixture. For automatic-selection cases, expose only normal skill metadata and the user task through a supported discovery environment; do not tell the agent which skill to select. Explicitly naming a skill cannot verify automatic discovery. Include unrelated E04/E05 and tiny-change E06/E29 controls in any selection trial.

Record `run ID/date; library and fixture revision or hashes; exact request; explicit versus automatic invocation; model/tool environment when available; permissions; actual output; rubric result with rationale; application-runtime status; limits`. If the runner cannot supply a model identity, say so. Retain only the minimal output excerpts and execution facts needed to substantiate the evaluation; no private repository content or full conversation transcripts are required.

For a useful comparative evaluation, hold model/settings, task, fixture and tool permissions constant and compare the previous revision or normal workflow with the candidate. Keep independent runs free of prior answers. Measure justified findings, unsupported findings, missed seeded faults, scope violations and truthful evidence; compare effort/tool calls where available. Include correct fixtures, not only seeded defects. Repeated runs can investigate variability; one small trial does not establish a reliability rate, universal framework coverage or improvement over an untested baseline. No new test runner, plugin or API spend is required merely to define these evaluations ([OpenAI evaluation guidance](https://developers.openai.com/blog/eval-skills)).

Rerun affected cases after a demonstrated instruction correction. Preserve failed evidence and explain the revision; do not change expected behaviour to match the output. The acceptance ledger tracks product assertions separately from this skill-evaluation rubric.

Static self-review found and resolved wording risks before delivery: candidate defaults now require adoption before consequential use; narrow UI changes need a delta rather than a full new spec; worked APIs and token values are explicitly fictional; static checks cannot close behavioural cases. Review also found that timeouts needed explicit request-generation retirement to exclude late replies for unchanged values. Both examples now define it; the form separately names reconciliation-pending and access-loss states. Normal implicit skill discovery was not changed. Remaining uncertainty is the actual model/tool behaviour under these cases.

Revision 1.1 static review additionally distinguishes large embedded features, nested component types and inline style syntax; separates token names from proven ownership/rendering; tests conditional AI selection; and makes small-change routing explicit. These cases invalidate any inference that the earlier E01-E16 review evaluated the new rules. E17-E29 are specification-level evaluations only until actual runs are recorded.
